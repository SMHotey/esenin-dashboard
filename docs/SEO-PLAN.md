# План оптимизации и поддержания poet-esenin.ru

Версия: 22.10.2026. Цель — обойти esenin.ru по посещаемости: дать больше полезных запросов,
лучше технически, регулярно обновляться.

## 1. Метрики, по которым понятно, что движемся в правильную сторону

- Доля индексированных страниц в Яндекс.Вебмастере и Google Search Console: цель 95 % из 500+ через 30 дней после включения HTTPS.
- Позиции по 20 целевым запросам («анализ стихотворения берёза», «история написания», «бунин? — нет, Есенин и Дункан», «музеи Есенина», «хронология жизни», «Есенин книга»). Смотреть раз в две недели в Вебмастере.
- CTR в выдаче: цель 5–8 % на информационные запросы. Если ниже — править заголовки в первую очередь.
- Глубина просмотра и время: цель 2+ страницы и 1,5 минуты на сессию.
- Скорость: LCP < 2,5 с (после Cloudflare и отложенной Метрики).

## 2. Ритм публикаций: как лучше

Рекомендую 1 публикацию в день по будням (≈ 5 в неделю, ≈ 20 в месяц), а не 2 в день.

Почему так:
- Статический сайт пересобирается деплоем; один материал в день стабильно обновляет сitemap, ленту и главную каждое утро, без пиков и провалов.
- Качество текстов важнее количества: одноразовый поток из 60 статей без выдержки датируется индексом, а ежедневный тихий рост выглядит естественнее для поисковиков и для читателя.
- Один человек пишет; при 2 в день на 90 дней потребуется 180 текстов — это падение качества и выгорание.

Альтернатива, если писать быстро и грамотно: 2 в день по понедельник-среду и 1 в день в четверг-пятницу. Но начинать лучше с 1 в день и поднять темп через месяц, когда появятся первые метрики.

Как это работает технически (уже сделано):
- `content/publications/<slug>.md` — один файл на публикацию; frontmatter: `title`, `slug`, `date` (YYYY-MM-DD), `category`, `excerpt`, `sources`.
- Сборка публикует только то, у кого `date` не позже сегодняшнего дня; будущие файлы лежат «в запасе».
- `.github/workflows/deploy.yml` пересобирает сайт каждый день в 06:30 МСК: публикация с сегодняшней датой выходит сама, без ручного деплоя.
- `npm run verify` проверяет: у выпущенной публикации есть страница, будущая не просочилась в dist, есть индекс журнала, дата корректная.
- Предпросмотр всех запланированных: `PUBLISH_ALL=1 npm run build` — локально, в деплой не идёт.
- Раздел: `/publications/` («Журнал» в меню), страницы `/publications/<slug>.html`, JSON-LD `Article`, записи в `sitemap.xml`, `search.json` и `feed.xml` (публикации идут первыми в ленте).

Требования к тексту публикации:
- 350–700 знаков текста плюс подзаголовки; это читается на телефоне и даёт 150–250 слов поисковой выжимки.
- Факты — из академических изданий (ПСС в 7 т., комментарии, мемуары с пометкой «мемуары»); формулировки — свои.
- Обязательно: 1–2 внутренние ссылки («Библиотека», «Темы», «Места», «Люди») и ссылка на источники.
- Заголовок — под конкретный запрос («история написания», «хронология», «как проверить»), не «Есенин и …» в общем виде.
- Опасаться чужих текстов: ни целиковых описаний с esenin.ru, ни музейных аннотаций.

## 4. HTTPS через Cloudflare (главная техническая задача)

Сейчас сайт живёт только по HTTP: GitHub не выпустил сертификат для poet-esenin.ru
(на 443 отдаётся сертификат *.github.io, что для браузера = несовпадение имени).
Пока HTTPS не включён, поисковики и браузеры трактуют сайт как ненадёжный.

Что нужно сделать вручную (≈ 15 минут, требует доступа к reg.ru и аккаунта Cloudflare):

1. Cloudflare → Add a site → `poet-esenin.ru` → тариф Free.
2. Проверить DNS: `@ A 185.199.108.153` · `109.153` · `110.153` · `111.153` и `www CNAME smhotey.github.io`.
   **Оранжевое облако (Proxied) НЕ включать** — схема проверена 22.10.2026: при проксировании у части
   провайдеров рвутся ответы крупнее ~24 КБ, а сертификат GitHub Pages вообще не выпускается (DNS
   указывает на Cloudflare, GitHub не может подтвердить домен). Рабочий вариант — «только DNS».
3. Скопировать два NS, выданные Cloudflare (вида `xxx.ns.cloudflare.com`).
4. reg.ru → управление `poet-esenin.ru` → «DNS-серверы» → изменить на выданные Cloudflare.
   Решение от 22.10.2026: **один домен на сайт**. `poet-esenin.online` не продлевается и не используется —
   редирект со второго домена даёт эффект только при наличии его собственной истории и ссылок, а у нового
   домена их нет; лишние зоны, сертификаты и продления — только расходы. Второй домен оправдан, если у него
   есть старые входящие ссылки (тогда 301 на основной) либо для языковых версий (тогда `hreflang`, не 301).
5. Дождаться делегирования: `nslookup poet-esenin.ru NS` должен показывать Cloudflare (обычно 5–30 минут).
6. Сертификат: его выпускает GitHub Pages (Let's Encrypt) автоматически, как только DNS указывает на GitHub —
   обычно минуты. Настройки SSL/TLS в Cloudflare при схеме «только DNS» не участвуют.
7. Когда статус сертификата станет `approved`: `gh api -X PUT repos/SMHotey/esenin-dashboard/pages -F https_enforced=true`.
8. Проверить: `https://poet-esenin.ru/` → 200 и валидный сертификат `CN=poet-esenin.ru`; `http://` → 301 на https;
   обложки книг (`/img/books/*.webp`) приходят целиком (это и был главный симптом при проксировании).
9. Если у провайдера всё же рвутся крупные ответы — проверить маршрут: `curl --resolve poet-esenin.ru:443:<другой IP CF>`
   и сравнить размер; при обрыве на ~24 КБ прокси не включать.

Могу сделать сам, если дадите Cloudflare API-токен (Scope: Zone:Edit, DNS:Edit) — создам зону, добавлю записи, покажу NS. Смену NS в reg.ru всё равно придётся подтвердить вручную.

## 5. Индексация и внешние сервисы

- Яндекс.Вебмастер: подтвердить домен через DNS TXT (запись создаётся в reg.ru или уже в Cloudflare), отправить `sitemap.xml` и `feed.xml`, включить «Индексирование» → проверку обхода.
- Google Search Console: подтвердить домен (DNS TXT), отправить карту сайта.
- После HTTPS — проверить оба сервиса: ошибки доступности, дубли, скорость.
- Бэклинки (вне сайта): тематические каталоги, литературные проекты, паблики, цитирование в СМИ. Без внешних ссылок top-3 по конкурентным запросам не берётся.

## 6. Технический бэклог

Сделано (проверено скриптом по 500+ страницам):
- 500 уникальных title/description/canonical, один h1, OG/Twitter, breadcrumbs.
- JSON-LD: Person (поэт + 32 человека), WebSite + SearchAction, WebPage, BreadcrumbList, CreativeWork, Place, ItemList, Book, FAQPage, DefinedTermSet, Article (включая публикации журнала).
- 400+ внутренних ссылок, глубина 2 клика, битых нет.
- Карта сайта с картинками (портрет + обложки), `llms.txt`, RSS-лента `feed.xml`.
- Метрика инициализируется после load, preconnect к `mc.yandex.ru`.
- Обложки книг 400 px, цены не публикуются, маркировка рекламы и `erid` — по каждой ссылке.

Осталось:
- HTTPS (п. 4) — критично.
- `lastmod` в карте сайта: сейчас одинаковый для всех, можно брать дату изменения данных.
- Критический CSS: инлайнить вышефолдовый блок (выигрыш 100–200 мс).
- Кэш GitHub Pages фиксированный — снимается Cloudflare.

## 7. Ритуалы поддержания

Что делает автоматика (без участия):
- Каждый день в 06:30 МСК — деплой: публикации с сегодняшней датой выходят сами.
- Каждый день в 05:00 МСК — `price-sync`: обновление цен и наличия книг.
- Каждый push в master — сборка + `npm run verify` (0 ошибок / 0 предупреждений — иначе деплой не проходит).

Еженедельно (≈ 30 минут):
- `npm run verify` локально перед публикацией новых материалов.
- Добавить 1–2 публикации в `content/publications/` по календарю.
- Просмотреть, что вышло в журнале и ленте, поправить заголовки, если заметили CTR ниже 4 %.

Ежеквартально:
- Аудит скриптом `seo_audit.py` (уникальность, тонкие страницы, глубина, сitemap).
- Сверка индексации в Вебмастере и Search Console.
- Ревизия календаря: что сработало по трафику, что перенести, какие темы добавить.

Ежегодно:
- Обновить даты последнего обновления в разделах биографии и «Версии».
- Проверить каталог книг: что изменилось в наличии, что устарело.
- Обновить README и этот план под новую реальность.

## 8. Проверка через 30/60/90 дней

Через 30 дней: HTTPS включён, оба сервиса индексации подтверждены, карта и лента отправлены, ≥ 20 публикаций в журнале, доля индексированных страниц 95 %+.
Через 60 дней: ≥ 40 публикаций, рост CTR по целевым запросам, есть первые позиции в топ-10 по «хвостовым» запросам (анализы, места, учебные вопросы).
Через 90 дней: ≥ 60 публикаций, видимый рост визитов из поиска по сравнению с базой (снимите базовый срез в Вебмастере сейчас), посещаемость превышает esenin.ru по ежедневным визитам.

Если через 30 дней роста нет — пересматриваем не технику, а запросы: смотрим, какие формулировки подхватил Яндекс, и расширяем по ним.
