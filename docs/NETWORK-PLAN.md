# План развития сети авторских сайтов

Утверждён: 22.10.2026. Основа — рекомендации по панели управления, шаблону, партнёрам и календарю публикаций. Отдельные ответы на вопросы о партнёрах и дружественных сайтах — в разделах 7.1 и 7.2.

Целевое состояние: сеть статических сайтов об одном или нескольких авторах, каждый — свой домен, свой репозиторий, один шаблон с набором скинов (п. 1.8) и настраиваемым набором модулей (п. 1.9), одна панель управления, автоматические публикации по расписанию и автозапуск каталога книг от нескольких партнёров.

## 0. Цели и метрики сети

- Один операционный цикл: новый сайт — от кнопки/команды до индексации в поиске без ручной правки кода.
- Панель: на одном экране видно все сайты — статус деплоя, SSL, индексации, очередь публикаций, визиты за вчера.
- Трафик: каждый сайт сравнивается с базой (первые 30 дней после запуска) и с прошлым месяцем.
- Качество: verify с нулём ошибок на всех сайтах; ни одного сайта с битым https, битыми ссылками или просочившейся будущей публикацией.

## 1. Этап 1. Тектоника шаблона (неделя 1)

Всё, что без чего сеть не подключается. Каждый пункт закрывается проверкой в verify или отчётом.

1.1 Версия шаблона
- В `site.config.json` поле `templateVersion` (сейчас фактически 1.0).
- В `scripts/verify.mjs`: сравнение с актуальной версией в шаблоне → предупреждение «сайт собран на устаревшем шаблоне».
- Версия — одна на шаблон, но минор растёт отдельно по трём осям: скины, модули, остальное. Смена набора скинов или схемы `modules` (п. 1.8–1.9) — это минор, и старые сайты не мигрируют принудительно: они остаются на своей версии, пока их не обновят по списку из реестра.
- Приёмка: правка версии в шаблоне делает старый сайт жёлтым на verify, но не блокирует деплой.

1.2 Единый отчёт при сборке
- Команда `npm run report` → `reports/site.json` со строгой схемой: `siteId`, домен, версия шаблона, число страниц, текстов, книг, публикаций выпущено/запланировано, дата последнего импорта книг, результат verify, размер dist, время сборки.
- Приёмка: схема JSON проверяется в verify; на всех сайтах формат идентичен.

1.3 Верификация поисковиков из config
- Поля `verification: { yandex: '...', google: '...' }` в config; layout подставляет meta-теги.
- Подтверждение нового домена в Вебмастере/ГСЧ — без правки кода.
- Приёмка: если поля нет — meta-тегов нет, ошибок нет; если есть — присутствуют в head.

1.4 Скрипт подключения домена в Cloudflare
- `scripts/cf-new-site.mjs --domain X`: создаёт зону, 4 A-записи GitHub + www CNAME (proxied), SSL Full, Always Use HTTPS, Brotli; печатает NS-пару для регистратора.
- Токен — из GitHub Secrets или локального файла, не в репозитории.
- Приёмка: подключение нового домена — одна команда, без ручных действий в API.

1.5 Настоящий шаблон репозитория
- Чистый репозиторий `author-site-template`: генератор, скиллы-скрипты, пустые `data/*.json`, примеры контента, без чужих текстов и картинок; включена кнопка «Use this template».
- Скаффолдер `wr new` переключается на клонирование шаблона (быстрее и чище текущей копии из esenin-dashboard).
- Приёмка: новый сайт поднимается из шаблона за 5 минут, `npm run verify` проходит.

1.6 Реестр сети
- Репозиторий `author-network` (приватный): `sites.json` — домен, репозиторий, счётчик Метрики, зона Cloudflare, регистратор, расписание публикаций, партнёр по умолчанию, версия шаблона, дата запуска; и `stats.json` — данные сборщика.
- Приёмка: в реестре есть записи для poet-esenin.ru и всех последующих сайтов.

1.7 Секреты и аккаунты
- GitHub Secrets на каждый репозиторий: Cloudflare-токен (если нужен скрипту), ничего больше.
- Один аккаунт Метрики на всю сеть, один Google-аккаунт под ГСЧ, один Cloudflare-аккаунт.
- Токен Cloudflare: два — широкий (только пока идёт настройка) и узкий `Zone:Edit + DNS:Edit` на постоянку; широкий отзывается после этапа.

1.8 Скины: облик вместо одинаковой вёрстки

Задача — не размножить шаблоны, а не выглядеть сетью клонов. Один код, разные облики; различия живут в CSS и в 3–4 флагах компоновки, а не в отдельной ветке шаблона.

- Поле `site.config.json → "skin": "classic" | "editorial" | "minimal" | "mono"` плюс `"skinOptions": { "nav": "top" | "side", "cards": "grid" | "list", "hero": "photo" | "text" | "split", "density": "normal" | "airy" }`.
- Реализация: `src/skins/<name>.css` — только токены (шрифтовая пара, ширина колонки, радиусы, тени, палитра, размеры заголовков) и флаги, которые layout читает одним объектом. Разметка страниц контента (works, people, places, poems) остаётся ОДНОЙ для всех скинов: иначе N обликов = N наборов багов и расхождений в JSON-LD.
- «Скин» и «тема» — разные вещи: скин — типографика, сетка, компоновка; тема — свет/тьма (по умолчанию тёмная). Каждый скин обязан корректно работать в обеих темах через переменные, а не через отдельный файл.
- Новый скин заводится, только если отличается минимум по 3 из 5 осей: шрифтовая пара, сетка карточек (grid/list), навигация (top/side), hero (photo/text/split), ширина и плотность колонки. Скин, отличающийся цветом акцента, — не скин, а настройка.
- Смена скина не меняет: набор страниц, URL, title/description, JSON-LD, доступность (контраст ≥ 4.5, фокус виден, `prefers-reduced-motion`), размещение блоков маркировки рекламы. Проверяется verify для любого значения `skin`.
- Проверка «не клон»: контрольная сумма собранного `styles.css` уникальна для каждого сайта сети; одинаковый CSS на двух доменах — ошибка verify. Скин и его флаги попадают в `reports/site.json` (п. 1.2).
- Приёмка: переключение `skin` в конфиге даёт визуально другой сайт без правки ни одного файла кода; все скины проходят verify с 0 ошибок.
- Состав на старте: 3 скина (classic — текущий есенинский, editorial — серифная книга, mono — плотный минимализм). Четвёртый — после третьего сайта, по факту надобности, а не заранее.

1.9 Модули: включение, порядок, подписи

Набор разделов перестаёт быть зашитым в код: сейчас меню — константа `nav` в `scripts/build.mjs:185`, подвал — ещё один хардкод, блоки главной печатаются всегда. Это и мешает сайтам различаться, и заставляет тащить пустые разделы.

- `site.config.json → "modules"`: объект, где ключ — id модуля, значение — `{ "enabled": true, "order": 2, "label": "Люди", "inHome": true }`. Порядок, подпись и участие в главной — данные, а не код.
- id модулей: `biography`, `life`, `people`, `works`, `topics`, `glossary`, `faq`, `places`, `legacy` (+ подмодули `legacy/gibel`, `legacy/memory`, `legacy/music`, `legacy/cinema`, `legacy/translations`), `books`, `publications`, `research`, `sources`, `versions`, `print`, `friends`.
- Обязательные, не отключаемые: главная, `about` (о проекте и правах), `privacy` (без неё нельзя включать счётчик), `404`, `sitemap.xml`, `robots.txt`, `search.json`. Они не входят в `modules` и печатаются всегда.
- Зависимости (модуль включается только при выполнении): `topics` ← `works` + `data/topics.json` (≥ 3 подборки); `glossary` ← `data/glossary.json` (≥ 20 слов с `forms[]`); `books` ← `data/books.json` + `affiliate.enabled`; `faq` ← `data/faq.json` (≥ 8 вопросов); `print` ← `works`; `friends` ← реестр сети `author-network/sites.json` и ≥ 2 соседних сайта; `legacy/*` ← соответствующий JSON (museums, monuments, music, films, languages). Нарушение зависимости — ошибка verify, а не пустая страница.
- Автовыключение по отсутствию данных: если данных нет, модуль выключается сам, причина пишется в `reports/site.json` (`"reason": "нет данных"`), пустая страница не печатается. Уже так работает пустой каталог книг — правило распространяется на все модули.
- Один источник правды: навигация (шапка + подвал), плитки и ленты главной, sitemap, `search.json`, `feed.xml`, `llms.txt`, JSON-LD и verify строятся из фактически собранных страниц и `modules`, а не из трёх независимых списков. Добавление модуля — одна запись в конфиг, а не пять правок.
- Отключение обязано убирать всё: страницы модуля, пункт меню, блок на главной, перекрёстные ссылки из других разделов («Все места →», «Читайте дальше», хлебные крошки), записи в поиске, sitemap и фиде. Приёмка: `modules.places.enabled=false` → в `dist` нет ни одной ссылки на `/places/`, verify зелёный, число страниц уменьшилось ровно на число страниц модуля.
- Дифференциация сайтов — побочный и главный эффект: у разных авторов разные набор, порядок и подписи разделов (у Есенина — музеи и музыка, у Бунина — Нобель и эмиграция), поэтому одинаковая структура на десяти доменах не воспроизводится механически. Пустые разделы «как в шаблоне» не выводятся.
- Приёмка: два сайта сети имеют разные меню и разный набор страниц, собранные из одного кода без правки `scripts/*.mjs`; `reports/site.json` содержит `modules: [{ id, enabled, order, pages, reason }]`.

## 2. Этап 2. Панель управления (неделя 2)

2.1 Сбор данных (`author-network/.github/workflows/collect.yml`, раз в сутки)
- GitHub API: статус последнего деплоя, версия workflow, время сборки.
- Cloudflare API: статус зоны, срок действия сертификата, https-доступность (HEAD-запрос).
- Яндекс.Метрика API: визиты, просмотры, глубина, доля отказов по каждому счётчику за вчера; токен один, счётчиков N.
- Search Console API: клики, показы, средняя позиция за 7 дней.
- Локальный аудит по каждому сайту: наш `seo_audit.py` (тонкие страницы, дубли, глубина, битые ссылки) + инвентаризация по уровням T1–T5 и наличию источников (п. 5.6).
- Результат дописывается в `stats.json`.

2.2 Отчёт панели (статика)
- `index.html` из `sites.json` + `stats.json`: таблица сайтов с цветом по колонкам (деплой, https, индексация, verify), очередь публикаций на 14 дней по всем сайтам, сводный график визитов, список «красных» задач.
- Колонки наполнения (п. 5.9): план/факт спринта, доля страниц T1–T4, доля страниц с источниками, тонкие страницы, свежесть ключевых страниц.
- Запуск: `npm run panel` локально или публикация в Actions.

2.3 Трафик отдельно
- Looker Studio (бесплатно): источники — Метрика (все счётчики) + Search Console (все сайты); общий дашборд визитов/позиций/CTR. Свой графический трафик в панель не переписываем.

2.4 Uptime и SSL-мониторинг
- В сборщике: HEAD по https, проверка срока сертификата Cloudflare (даты), оповещение — пока в виде «красного» в панели; при необходимости — Telegram/почта.

## 3. Этап 3. Каталог книг: партнёры и подкатегории (неделя 3)

3.1 Реестр партнёров — `data/partners.json`
Каждый партнёр описывается данными, а не кодом:
```
{
  "id": "chitai-gorod",
  "name": "Читай-город",
  "enabled": true,
  "linkType": "chitai",              // тип адаптера ссылок
  "priceType": "jsonld",             // откуда цена/наличие
  "adapter": "chitai-gorod",         // адаптер импорта каталога
  "advertiser": "Рекламодатель ООО «ГРАМОТА», ОГРН 1037706012376.",
  "erid": true,                      // выводить erid
  "priority": 1                      // порядок кнопок
}
```
- Добавление нового партнёра = новый объект в JSON плюс, если у него своя логика, файл-адаптер в `scripts/partners/<id>.mjs`. Код каталога, кнопок и цен к партнёру не привязан.
- Маркировка рекламы берётся из `advertiser` партнёра — у разных партнёров свой оператор и свои требования к раскрытию.
- Приёмка: отключение партнёра (`enabled: false`) убирает его кнопки и ссылки из всех карточек без правки шаблона.

3.2 Поддержка второго партнёра
- Кандидаты на проверку интерфейса — ЛитРес и Озон (у обоих партнёрские программы, но свой формат ссылки и свои требования к раскрытию). Итоговый список — после проверки на них адаптера; финализировать на старте не нужно.
- Порядок: адаптер импорта каталога → `books-source-<partner>.json` → генерация партнёрской ссылки через кабинет/сервис партнёра → проверка редиректа и сопоставление productId → `data/books.json`.
- Мультипривязка книги: поле `links: {chitai_gorod: {...}, litres: {...}}` (поле уже есть, расширяем); карточка книги показывает кнопки только тех партнёров, которые есть у книги и включены в `partners.json`.
- Приёмка: книга с двумя партнёрами показывает две кнопки, обе с корректной маркировкой; verify проверяет erid и раскрытие на каждой ссылке.

3.3 Подкатегории книг: бумажные / электронные / аудио
- Нормализация формата при импорте: `formatType: "paper" | "ebook" | "audio"` (из названия формата и категории каталога); в JSON-LD соответственно `Hardcover` / `EBook` / `Audiobook` (уже так).
- UI раздела «Книги»: строка фильтров «Все · Бумажные · Электронные · Аудио», счётчики, состояние в URL (`/books/?format=paper`) — ссылки индексируемы и шарятся.
- Если по какому-то типу книг нет — фильтр скрывается, а не показывает пустоту.
- Панель: в `reports/site.json` — разбивка по типам, чтобы видеть, каким типам не хватает данных.
- Приёмка: все три фильтра работают, в URL состояние сохраняется, verify: у каждой книги `formatType` заполнен.

3.4 Автоматизация обновления каталога
- Ежедневный workflow: цена/наличие — как сейчас (`sync-prices.mjs`), плюс (по возможности) перепроверка каталога нового партнёра с учётом rate-limit и кулдаунов.
- Ручной импорт остаётся для добавления новых книг; полный автоимпорт — если партнёр даёт стабильный источник без блокировок.

## 4. Этап 4. Дружественные сайты и кластерная перелинковка (неделя 4)

4.1 Страница каталога на каждом сайте — `/friends/`
- Источник — тот же `author-network/sites.json` (домен, автор, 2–3 предложения о сайте).
- Каждый сайт пишет описание соседей СВОИМИ словами: одинаковый текст каталога на десяти доменах = дублирование контента и признак ссылочной сети. Персонализация обязательна (проверка: тексты описаний на разных сайтах не совпадают дословно).
- Подвал сайта: одна ссылка «Соседние проекты» → на `/friends/`. Никаких ссылок на все домены в подвале каждой страницы.

4.2 Контекстные ссылки
- В публикациях журнала: «об этом же в проекте о Блоке» — 1–2 ссылки там, где реально уместно.
- В разделах «Люди» и «Места»: ссылка на соседний сайт, если тема смежная.
- Анкоры разные, описания живые, ссылки ведут на конкретные страницы соседей, а не только на главные.

4.3 Польза для SEO (честно)
- Зачтётся: внешние ссылки с тематически близких доменов передают вес, помогают быстрой индексации нового сайта и выглядят естественно, если ведут с релевантных страниц.
- Риск: взаимный перелинкованный каталог без контекста (footer-ссылки, одинаковые анкоры) поисковики обесценивают, в худшем случае трактуют как ссылочную сеть. Поэтому правила из 4.1–4.2 обязательны, а не рекомендательны.
- Дополнительно: страница каталога полезна читателю и сама по себе привлекает переходы; её могут цитировать.
- Не делать: обмен ссылками на сторонних площадках, заказные сетки, одинаковый анкор на всех сайтах, ссылки в скрытых блоках.

## 5. Наполнение и обновление: что делает сайт непохожим

Раздел закрывает главную слабость текущего состояния: страницы собраны из фактов, которые есть в полусотне других мест — даты, имена, пересказы биографии. Читатель получает ровно то же, что и везде, поэтому не остаётся, не возвращается и не ссылается. «Огрызки» — не вопрос стиля, а следствие: страница описывает факт, но не даёт ничего, чего у читателя не было. Пункты 5.1–5.9 — обязательные правила для всех сайтов сети, а не пожелания.

5.1 Пять уровней ценности (T1–T5)
- T1 «Документ»: то, чего нет в сети в удобном виде — письма, дневники, прижизненные рецензии, газетные публикации, обложки первых изданий, автографы. Формат: транскрипт + скан/факсимиле + наш комментарий (что это, откуда, что из него следует).
- T2 «Расчёт»: посчитанное нами по корпусу — частоты слов, распределение по годам, длина строки, редкие слова, сравнение редакций, статистика переводов, хронологические плотности. Формат: таблица или график + методика + вывод.
- T3 «Синтез»: сравнительные таблицы, карты, генеалогия, хронологии с фильтрами, маршруты по местам, «кто с кем и когда». Ценность — в сведении того, что раньше лежало в десяти разных источниках.
- T4 «Разбор»: спорные вопросы и мифы — что утверждают, откуда пошло, что говорят источники, статус достоверности A–D (`data/sources.json`). Именно эти страницы цитируют и обсуждают.
- T5 «Справочник»: биография, люди, места, FAQ, словарь — нужны для полноты и трафика, но сами по себе ценности не создают.
- Правило: не меньше 60% страниц сайта — T1–T4. Раздел не растёт в T5, пока не закрыт T1–T4 по своей теме. Поэтические тексты (T1 по своей природе) считаются отдельно и в эти 60% не входят.

5.2 Стандарт страницы: пять обязательных элементов
- Первоисточник или расчёт: ссылка на документ, скан, таблица с методикой. Если проверить нечем — это T5, и такие страницы не растут.
- Один нетривиальный вывод, которого нет в пересказах: не «родился в Константинове», а «в 1914–1916 гг. у него X публикаций в московской прессе, из них Y — в изданиях, закрывшихся к 1918-му».
- Якорь: цитируемая единица — дата, цифра, строка из документа. Без якоря страницу не пересказывают и не ссылаются на неё.
- Явные сомнения: что неизвестно, где источники расходятся, чему мы не верим и почему. Честная неопределённость работает лучше уверенного пересказа.
- Связка: 3–5 осмысленных ссылок на соседние страницы по теме, а не блок «читайте также» со случайной выборкой.
- Объём: исследовательская страница (T1–T4) — от 4000 знаков и хотя бы один документ/таблица/расчёт; описательная (T5) — от 1500 знаков. Страницы текстов произведений под правило объёма не попадают: там ценность — сам текст.

5.3 Откуда брать нетривиальное
- Первоисточники в общественном достоянии: Викитека, archive.org, НЭБ/РГБ (просмотр), сканы периодики 1900–1930-х, мемуары и переписка. Правило: транскрибируем один раз, используем много раз — пул документов общий для сети, комментарии к ним пишутся отдельно для каждого автора.
- Корпусные расчёты: один движок анализа на сеть (`scripts/analyze/*.mjs`: частоты, n-граммы, годы, длина строки, уникальные слова, сравнение редакций). Код общий, данные и выводы — свои. Это самый дешёвый способ получить T2 в промышленных объёмах.
- Сведение: карты (места, маршруты), генеалогия, таблицы «событие → документ → что из этого следует», хронологии по дням.
- Музейные и архивные данные: факты (адреса, фонды, номера дел, даты выставок) брать можно, формулировки описаний — нет; своя аннотация обязательна.
- Запрещено: пересказ чужих статей и очерков, «интересные факты» без источника, копирование описаний музеев и магазинов, тексты с сайтов-конкурентов даже в переработанном виде.

5.4 Серии и кластеры: единица работы
Работаем не «по разделу», а по серии — повторяемой структуре, которую наполняют свои данные. Серия переносится на любого автора, данные каждый раз уникальны, поэтому сеть не превращается в клоны:
- «Первая публикация»: факсимиле, транскрипт, что автор изменил в книжном варианте.
- «Черновик и финал»: сопоставление редакций построчно (уже есть в `data/versions.json`).
- «Слово в корпусе»: частоты, слова-однократники, рост и падение по годам.
- «Критика при жизни»: рецензии 1900–1930-х с нашей аннотацией и оценкой пристрастности.
- «Одно стихотворение в N переводах»: сравнение переводов по строкам, что теряется.
- «Спорный вопрос»: досье — версии, источники, статус достоверности, наша позиция.
- «География»: карта точек и маршрутов, практическая часть (как добраться, что рядом).
- «Экран и музыка»: не список, а разбор — что исказили, что совпало, кого играли лучше.
- «Хронология дня»: один день по часам и документам (28 декабря 1925 — эталонный пример).
- «Учебник против источников»: разбор школьных штампов со ссылками на документы.
- «Забытое и приписанное»: тексты вне канона, апокрифы, ошибочные атрибуции.
- На первый год на каждом сайте — минимум 4 серии, из них 2 «якорные» (T1 и T2). Серия считается закрытой, когда в ней 8–12 материалов: тогда она становится отдельной посадочной страницей с оглавлением.

5.5 Ритм: спринт по кластеру вместо «публикации в день»
- Единица планирования — неделя и кластер, а не день и страница. Недельный спринт: 1 якорный материал (T1 или T2), 2–3 средних (T3/T4), обновление 2 старых страниц.
- Ежедневный деплой остаётся, но он публикует то, что уже написано; публикация в журнале — переупаковка готового материала (анонс + выжимка + ссылки), а не отдельная единица контента. Пустой журнал лучше журнала ради журнала.
- Кластер ведётся до глубины, а не размазывается: пока «Переводы» не закрыты 8–12 материалами, не начинаем «Музыку». Так раздел за 3–4 недели становится лучшим в рунете по теме, а не средним по тридцати темам.
- Календарь (60 тем в `docs/SEO-PLAN.md`) переписывается под серии: строка календаря = серия + конкретный материал, с указанием типа (T1–T4) и источника, который для него нужен.

5.6 Программа подъёма существующих страниц
- Инвентаризация: скрипт размечает уже собранные страницы по T-уровням, считает объём и наличие источников. Ожидаемый результат — большинство текущих страниц окажется T5.
- Для каждой T5-страницы — «доливка» одного уникального элемента: документ, цифра, сравнительная таблица или разбор расхождения. Не переписывать заново, а добавлять то, чего нет.
- Страницы, которым доливка не помогает (нет ни источника, ни данных), — объединять с соседней и ставить 301, а не держать ради счётчика страниц.
- Порядок: сначала посадочные разделы и то, что уже приносит показы в Вебмастере/ГСЧ (там доливка даёт быстрый эффект), потом всё остальное.

5.7 Обновление: что и когда
- Материалы делятся на датозависимые (цены, наличие, ссылки партнёров, «сколько сейчас музеев», афиши) и канонические (тексты, анализ, документы). Датозависимые обновляются автоматически (`sync-prices.mjs`), канонические — по календарю ревизий.
- Естественные поводы для ревизии: годовщина рождения и смерти, выход новой книги или выставки, публикация архива. Обновление к дате — законный повод, если содержание реально меняется.
- `dateModified` меняется только при содержательной правке. Массовое «обновлено к годовщине» без изменений поиск видит по диффу и обесценивает; такое не делаем.
- Раз в квартал: пересмотр тонких страниц — если за 90 дней ни одного перехода из поиска и меньше 1500 знаков, страница сливается с соседней (301) или дополняется.
- Раз в год на сайт: ревизия фактов в ключевых разделах (биография, хронология, места) — сверка с новыми публикациями, отметка в `sources.json`.
- Никогда: новости ради новостей, «сегодня день рождения поэта» без нового содержания, автоматическая генерация абзацев из данных без проверки человеком.

5.8 Как это масштабируется на сеть
- Общее: движок анализа, пул документов, методика серий, чек-лист страницы, гейты проверки. Это не дублирование контента — это инструмент.
- Уникальное: данные, выводы, комментарии, подборки, аннотации — на каждом сайте свои.
- Запрет на переиспользование абзацев между сайтами; проверка — кросс-сайтовые шинглы по `dist` (общих шинглов меньше ~10%, и только служебные фразы). Совпадение абзацев — ошибка verify.
- Материал «на стыке» авторов (например «два взгляда на деревню») публикуется один раз, на одном сайте, со ссылкой с соседнего — а не двумя копиями.
- Одинаковые данные партнёров (каталог книг) не считаются уникальным контентом: ценность карточки — в нашей аннотации, а не в описании магазина.

5.9 Что видно в панели (метрики наполнения)
- План/факт по спринтам: сколько якорных и средних материалов выпущено за неделю по каждому сайту.
- Доля страниц T1–T4 и средний объём исследовательских страниц.
- Доля страниц с источниками (`sources[]` не пуст) — по разделам.
- Тонкие страницы (кандидаты на слияние) и страницы без переходов из поиска за 90 дней.
- Свежесть: сколько ключевых страниц не обновлялось больше года.
- Приёмка: панель показывает эти шесть показателей по каждому сайту, и по ним же строится месячный отчёт «сделано / не сделано».

## 6. Постоянный контур (не заканчивается никогда)

- Наполнение: недельный спринт по кластеру (п. 5.5) — 1 якорный материал, 2–3 средних, 2 обновления. Календари серий — `docs/SEO-PLAN.md` на каждом сайте, позже — общий в реестре сети. Автодеплой в 06:30 МСК.
- Книги: ежедневная проверка цен/наличия, раз в месяц — ревизия каталога.
- Аудит: раз в месяц `seo_audit.py` по каждому сайту, результат в панель.
- Индексация: сначала — Вебмастер и Search Console вручную; когда сайтов станет 3+, автоматизируем отправку sitemap через API из сборщика.
- HTTPS/Cloudflare: мониторинг сертификата — в панели (п. 2.4).
- Шаблон: раз в квартал — ревизия версии шаблона и обновление старых сайтов по списку из реестра.

## 7. Ответы на открытые вопросы

### 7.1 Нужно ли финализировать список партнёров на старте — нет, но…
- Финализировать не нужно: интерфейс описан данными (`partners.json`), новый партнёр добавляется без правки шаблона.
- Но проверить адаптер на 2–3 разных партнёрах нужно рано: именно различия (формат ссылки, требование к меткам, источник цены, правила раскрытия) вскрывают архитектурные дыры. На первом сайте это делаем со вторым партнёром — до размножения сети.
- Что реально нужно решить на старте: аккаунт партнёрской программы (один на всю сеть, чтобы ссылки были от одного издателя) и текст раскрытия рекламы для каждого партнёра — он вшивается в config и не должен меняться постфактум.
- Кандидаты на проверку: ЛитРес, Озон. Проверка = каталог партнёра → генерация ссылки → валидация редиректа → карточка на сайте. Если у кого-то нет нормальной партнёрской механики или ассортимента по автору — не берём.

### 7.2 Дружественные сайты — зачтётся ли в SEO
- Да, при выполнении правил из раздела 4: релевантные страницы, живые анкоры, персонализированные описания, одна ссылка в подвале, а остальное — контекст.
- Это же кластерная перелинковка: сайт нового автора получает вес от уже индексируемых соседей, что ускоряет выход в индекс после запуска.
- Полный текст правил и объяснение рисков — в разделе 4.3.

## 8. Сроки и контрольные точки

- Неделя 1: этап 1 закрыт — verify знает про версию шаблона и скин, отчёт `reports/site.json` есть (в нём `skin`, `modules[]`), `cf-new-site.mjs` работает, реестр сети создан; на двух скинах сборка проходит verify, выключение модуля убирает его страницы и ссылки без правки кода.
- Неделя 2: панель показывает два сайта с колонками деплой/https/индексация и очередью публикаций; Looker Studio подключён к Метрике.
- Неделя 3: в каталоге книг есть фильтр «Бумажные/Электронные/Аудио» и второй партнёр либо подтверждён, либо отклонён по результатам проверки адаптера.
- Неделя 4: на всех сайтах работает `/friends/` с персонализированными описаниями и хотя бы пара контекстных ссылок в журналах.
- День 30: панель обновляется автоматически; первый отчёт по сети сверен с базовыми цифрами трафика.

Контент идёт параллельно этапам, а не после них (п. 5.5–5.6):
- Неделя 1: инвентаризация всех страниц по уровням T1–T5 скриптом; список «доливок» на первые 50 страниц.
- Неделя 2: два первых материала T1 (документ) и один T2 (расчёт); серии занесены в календарь вместо тем-однодневок.
- Неделя 4: одна серия закрыта (8–12 материалов) на первом сайте; доливка 15 страниц T5.
- День 60: две серии закрыты; 25 страниц получили документ или расчёт.
- День 90: у первого сайта не меньше 60% описательных страниц — T1–T4; у второго сайта 4 серии, из них 2 якорные; панель показывает план/факт по спринтам.

## 9. Чего в плане пока нет (решается до запуска второго сайта)

Эти пункты не про SEO, но без них сеть не переживёт третий сайт. Порядок — по цене ошибки.

9.1 Деньги и правовое оформление
- Партнёрские выплаты требуют оформленного получателя дохода (самозанятость или ИП) и действующего договора с программой; реквизиты и договор — вне репозитория.
- Cookie и трекинг: «Политика конфиденциальности» есть; нужно решить, требуется ли отдельное уведомление о cookie при текущей настройке Метрики (без сторонней рекламы) — один раз, с юристом, и зафиксировать решение в `docs/`.
- Сканы и факсимиле: фиксируем правило — берём только то, что в общественном достоянии или разрешено лицензией источника, с указанием держателя и ссылкой. Спорные случаи не публикуем.

9.2 Резервные копии и большие файлы
- Тексты, данные и код — в git. Сканы документов в git не кладём: лимиты GitHub (100 МБ на файл, ~1 ГБ Pages) не резиновые. Решение: скан лежит во внешнем хранилище (archive.org / собственный бакет), на сайте — предпросмотр и ссылка.
- Раз в квартал — проверка восстановления: клон репозитория на чистой машине, `npm ci && npm run verify`, деплой. Бэкап, который не проверяли, не считается.

9.3 Ресурсы и роли
- Бюджет времени: ~8 часов в неделю на сайт в постоянном режиме (1 якорный материал, 2–3 средних, обновления, разбор ошибок). Для 5 сайтов это 40 часов — значит, либо серии автоматизируются движком, либо сайтов меньше. Оценку зафиксировать честно, а не «сделаем как-нибудь».
- Роли по шагам, даже если исполняет один человек: автор → фактчекер (проверка по источникам A/B) → сборка/verify → публикация. Фактчек отдельным проходом, а не «по ходу».

9.4 Аккаунты и доступы
- 2FA на GitHub, Cloudflare, Метрике, Вебмастере, ГСЧ, регистраторе, партнёрской программе. Коды восстановления — вне браузера.
- Два администратора у регистратора и Cloudflare: потеря единственного доступа = потеря домена и DNS.
- Автопродление доменов включено, напоминание за 60 дней. Домен — самый дешёвый актив и самый дорогой в восстановлении.

9.5 Метрики успеха и точка отказа
- Цели первого сайта: индексация ≥ 90% страниц за 60 дней; ≥ 100 визитов в день к 6 месяцам; ≥ 2% переходов в карточку книги из просмотров раздела «Книги».
- Правило расширения: следующий сайт открывается, только если предыдущий вышел на 50% целевого трафика. Если за 6 месяцев сайт даёт меньше 20 визитов в день — следующий не открываем, разбираемся с первым (спрос, качество, индексация).

9.6 Производительность
- Бюджет: LCP < 2,5 с на мобильном, CLS < 0,1, вес страницы без обложек < 500 КБ, JS не блокирует отрисовку. Замер — в панель по каждому сайту, а не «на глаз» в браузере.

9.7 Обратная связь читателей
- Один адрес для сообщений об ошибках, шаблон ответа, срок реакции 7 дней. Исправление попадает в журнал изменений страницы (`dateModified` + короткая запись «исправлено: …»).
- Это же канал фактчека: читатели находят ошибки быстрее, чем внутренний аудит.

9.8 Риски и план Б
- Домен не продлён / потерян: автопродление, второй админ, копия контента живёт в git — сайт поднимается на новом домене за час, но позиции теряются; поэтому домены продлеваем на 5 лет вперёд.
- Партнёрская программа закрылась: карточки книг остаются с поисковыми ссылками без партнёрского вознаграждения, раздел не удаляем.
- Поисковик наложил фильтр: сначала проверяем дубли и тонкие страницы (п. 5.6–5.7), потом перелинковку (п. 4), и только потом — переписывание.
- Cloudflare недоступен или аккаунт заблокирован: DNS переключается на регистратора (A-записи GitHub известны), сайт продолжает работать без прокси и кэша.

9.9 Монетизация за пределами книг
- Реклама, донаты, лицензирование сканов — не раньше, чем через 6 месяцев и только по фактическому трафику. Решение фиксируется отдельно; в шаблон ничего не встраиваем заранее.

9.10 Журнал изменений сайта
- Страница «Что нового» (или блок на главной) из уже существующих публикаций и правок: честная история и повод для повторного обхода. Одинаковых заголовков между сайтами не делать.
