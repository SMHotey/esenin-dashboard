## Роль и цель

Ты — программист сайта о Есенине. Задача: заставить сборку размечать 17 непоэтических
текстов библиотеки на абзацы с типами (`p`, `verse`, `part`, `date`, `head`), не потеряв
ни одного знака исходного текста, и закрыть эту разметку гейтами в `verify`. Стихи и поэмы
(388 текстов) и 8 коротких непоэтических текстов остаются байт-в-байт как сейчас. Кнопку
книги, `book.js`, CSS и звук НЕ делаешь — это шаги S2-S5.

## Что сделать

**T1. Конфиг охвата — `site.config.json`.** Добавить раздел `reader` с единственным ключом
`book`:

    "reader": {
      "book": {
        "genres": ["Проза", "Статья", "Автобиография"],
        "minChars": 1500
      }
    }

Ровно эти два ключа: `available` и `sound` появятся в S2 и S4, вперёд их не заводить.
Место — после раздела `home`, до `affiliate`.

**T2. Файл переопределений — `data/book-overrides.json` (новый).** Содержимое — пустой
объект `{}` (JSON без комментариев). Схема на будущее (реализуется загрузчиком, но записей
сейчас нет):

    { "slug-текста": {
        "types": [ { "text": "точная строка после trim", "type": "verse" } ],
        "lineParagraphs": true } }

`type` — одно из `p`, `verse`, `part`, `date`, `head`. `lineParagraphs: true` включает
построчный режим для всего текста. Загрузчик в `scripts/build.mjs`:
`await readJson("data/book-overrides.json", {})` (хелпер `readJson` — `scripts/build.mjs:12`,
конфиг читается так же на строке 21). Правила загрузчика: `slug` не из `works.json` —
ошибка сборки; неизвестный `type` — ошибка сборки; правило `types` применяется до
построчного разбора по точному совпадению строки после `trim` (все вхождения).

**T3. Функция разметки — `scripts/build.mjs`.** Чистая функция
`bookParagraphs(text, override)` → массив блоков `{ type, text }`, правила БП1-БП7:

- **БП1.** `\r` убрать; каждую строку обрезать по краям; три и более переводов строки
  свести к двум (двойной перевод строки = граница абзаца).
- **БП2.** Разбить на блоки по пустой строке.
- **БП3.** Блок из 2+ строк, где **каждая** строка ≤ 55 знаков, — целиком `verse`: строки
  сохраняются как есть, в разметке соединяются тегом `br`.
- **БП4.** Иначе: если в блоке 2+ строк и **медиана** длин строк ≥ 56 — блок разбирается
  построчно, то есть каждая содержательная строка становится своим абзацем. Короткие строки
  такого блока тоже становятся отдельными абзацами (это и даёт 20/27/27 абзацев
  автобиографий). Если медиана < 56 — строки блока склеиваются в один абзац через пробел.
- **БП5.** Порядок проверок строки внутри блока:
  1. `^\d{1,4}$` → `date`, если это `^(19|20)\d\d$`, иначе `part`;
  2. `^[IVX]+\.?$` → `part`;
  3. капслок: длина ≤ 40, строка равна своему верхнему регистру, содержит буквы, **не**
     заканчивается на `.` `!` `?` `—` → `head`;
  4. иначе содержательная строка: в построчном режиме — свой абзац, в обычном — в буфер.
- **БП6.** Буфер сбрасывается в блок `p` перед каждым структурным блоком и в конце блока;
  строки буфера соединяются одним пробелом.
- **БП7.** Переопределение из T2 применяется к строке до проверок БП3-БП5 и заменяет тип
  найденного блока.

**T4. Отбор и вывод — `scripts/build.mjs`.** Один раз рядом с загрузкой `works`
(`scripts/build.mjs:138`) посчитать набор:

    const bookCfg = config.reader?.book || {};
    const bookGenres = new Set(bookCfg.genres || []);
    const bookMin = Number(bookCfg.minChars) || 1500;
    const bookSlugs = new Set(works.filter((w) => bookGenres.has(w.genre) && (w.chars || 0) >= bookMin).map((w) => w.slug));

В `workPage` (`scripts/build.mjs:1152`) заменить строку 1183: для slug из `bookSlugs` —
обёртка `div` с атрибутами `class="poem"` и `data-book-source`, внутри абзацы; для остальных
ровно как сейчас — `div class="poem"` и `${esc(w.text)}` внутри.

**T5. Разметка блоков (точная форма).** Обёртка: `div` с атрибутами `class="poem"` и
`data-book-source`. Внутри — блоки по таблице; каждый текст прогоняется через `esc()`:

| тип блока | разметка |
|---|---|
| `p` | `p` без атрибутов |
| `part` | `p` с атрибутом `class="book-part"` |
| `date` | `p` с атрибутом `class="book-date"` |
| `head` | `h3` с атрибутом `class="book-head"` |
| `verse` | `div` с атрибутом `class="book-verse"`, строки внутри соединены тегом `br` |

Между тегами — **ни одного перевода строки и ни одного отступа**: у `.poem` включён
`white-space: pre-wrap` (F2), и пробелы форматирования дадут пустые строки на экране.
Стили не правим (запрет 2), поэтому это обязательное условие.

**T6. Строка отчёта — `scripts/build.mjs`.** Требование плана «сумма текста абзацев равна
`chars`» понимается так (решение R3, иначе требование невыполнимо буквально): переводы строк
разрешено заменять пробелами, поэтому сверяется **текст**, а не длина в байтах:
`collapse(склейка абзацев)` должно быть равно `collapse(нормализованный источник)`, где
`collapse` = схлопнуть все пробельные серии в один пробел и обрезать края. Второй
независимый инвариант — `w.chars === w.text.length`, он уже истинен для всех 413 записей
(F3) и в этом шаге не проверяется. Потеря любого непробельного знака ловится первым
равенством. В конце сборки напечатать ровно:

    book: 17 текстов, 0 расхождений

где 17 — число отобранных, 0 — число текстов, где схлопнутые строки не совпали. Если
расхождений больше нуля — после печати строки поставить `process.exitCode = 1` и напечатать
в `stderr` перечень slug'ов. Строка печатается всегда (в том числе при нуле).

**T7. Гейты — `scripts/verify.mjs`.** Новый блок сразу после проверок произведений
(`scripts/verify.mjs:361-370`), стиль — `errors.push(...)` с адресом страницы:

- **V1.** `config.reader.book.genres` — непустой массив, `minChars` — число > 0; иначе ошибка
  «site.config.json: нет reader.book.genres/minChars».
- **V2.** Отобрано по конфигу ровно 17 текстов; иначе ошибка с фактическим числом (гейт
  «Готово =» плана: 17).
- **V3.** Страниц `works/*.html` с атрибутом `data-book-source` ровно 17, и это те же slug'и;
  у остальных страниц произведений атрибута нет. Список страниц брать из `htmlFiles`.
- **V4.** Для каждой из 17 страниц: вырезать содержимое обёртки (искать
  `class="poem" data-book-source`, затем идти по тегам и считать баланс открывающих и
  закрывающих `div`, чтобы не оборваться на вложенном `book-verse`), снять теги, заменить
  `br` на пробел, раскодировать `&amp;` `&lt;` `&gt;` `&quot;` (`&amp;` — последним),
  схлопнуть пробелы и сравнить с `collapse(w.text)`. Расхождение — ошибка с адресом страницы
  и позицией первого несовпадения.
- **V5.** Типовые счётчики (замер, ожидание): `book-verse` — 11 в `ярославны-плачут`, 3 в
  `ключи-марии`, 2 в `отчее-слово`, 1 в `о-сборниках-произведений-пролетарских-писателей`;
  `book-part` — 2 в `железный-миргород`, 3 в `у-белой-воды`; `book-head` — 5 в
  `железный-миргород`; `book-date` — 1 в `avtobiografiya-1923` со значением `1923`.
  Считать вхождения, а не строки файла. Плюс: в `железный-миргород` нет абзаца `p` с текстом
  ровно `I` или `II`, в `у-белой-воды` нет абзаца с текстом `1`, `2`, `3`.
- **V6.** В `info` добавить строку вида `book: 17 текстов, N абзацев` (N — сумма блоков по 17
  текстам, замер даёт 575; при другом N ошибка V4 или V5 уже сработает раньше).

**T8. Разовая сверка (не в репозиторий).** Положить в `scratch/book-check.mjs` скрипт,

## Как проверить (гейты)

Все прогоны — из корня репозитория, оболочка bash (git-bash), Node 24. Логи — в `reports/`
(каталог в `.gitignore`), большой вывод не печатать целиком. Порядок обязателен: G0 до
первой правки, остальные после.

**G0. Базовый прогон ДО правок.** Нужен, чтобы отличить свои поломки от чужих.

## Стоп-сигналы

Останавливайся и докладывай, не «адаптируя по смыслу»:

- **S1.** Отбор по `reader.book` даёт не 17 текстов — доложить фактическое число и состав
  (`genre`, `chars` не попавших). Порог и жанры подгонять нельзя: это решение владельца.
- **S2.** Правила БП дают счётчики, отличные от замеренных (11/3/2/1 `verse`, 2+3 `part`,
  5 `head`, 1 `date`, 566 блоков) — доложить, где расходится, и своё понимание причины.
  Понижать ожидания в `verify` или подгонять правила под числа запрещено.
- **S3.** Для прохождения гейта нужна правка `src/styles.css`, `src/app.js`,
  `data/works.json` или самого текста — это вне объёма шага; стоп.
- **S4.** Приходится вписывать записи в `data/book-overrides.json`, чтобы получить ожидаемые
  счётчики: значит правило конфликтует с материалом — стоп с разбором конкретного места.
- **S5.** `npm run verify` красный по причине, не связанной с шагом (ссылки, цены, sitemap,
  журнал): зафиксировать разницу с baseline G0 и не «чинить» чужие проверки.
- **S6.** `npm run verify` даёт предупреждения, которых не было в baseline: разобрать до
  нуля новых; ослаблять проверку нельзя.
- **S7.** Форма обёртки или разметки требуется другой из-за S2-S3 (книга ждёт
  `.poem[data-book-source]`) — стоп: это меняет контракт следующих шагов.

## Формат отчёта

Отчёт — в карточку шага, на русском, до коммита и без пересказа кода. Порядок разделов:

1. **Что сделано** — по пунктам T1-T8, с адресами (`файл:строка`), одной строкой на пункт.
2. **Baseline** — цифра из G0: `предупреждений N` до правок.
3. **Сборка** — фактическая строка `book: ...` из G1 и `EXIT`.
4. **Полный гейт** — строка `ПРОВЕРКА ...` из G2 и `EXIT` (ошибок и предупреждений — числа).
5. **Сверка текста** — `texts / ok / diffs` из G3 и `EXIT`.
6. **Счётчики типов** — вывод `node scratch/book-check.mjs --types` целиком (17 строк) и
   итог 575; отдельно — что не совпало с таблицей ожиданий, если не совпало.
7. **Расхождения** — что в плане не совпало с кодом или данными (минимум: части «Железного
   Миргорода» I-II вместо I-IV; решение R2 про медиану) и как это отражено в комментариях
   кода. Комментарии — по-русски.
8. **Коммит** — `git add` перечислением четырёх файлов (не `-A`), сообщение на русском,
   `git push`, полный sha. В журнал плана строку НЕ добавлять: её пишет страж после APPROVE.

Если гейт не сходится и обойдён быть не может — в отчёте раздел «Не сделано» с причиной и
точным местом, а не «почти готово».

## Вопросы

**В1. «Железный Миргород»: 2 части вместо 4 — как быть?** В данных только «I» и «II».
Вариант A (принят по умолчанию): правило общее, гейт ждёт 2 части, план получает пометку в
отчёте. Вариант B: искать полный текст с частями III-IV в другом источнике — это отдельная
задача наполнения данных, вне S1. Цена A — ноль, цена B — новый источник и перезаливка
текста.

**В2. «О себе»: первая строка текста дублирует заголовок страницы — оставить абзацем?**
Вариант A (принят): строка остаётся обычным абзацем, дубль виден в книге — правится позже в
S7 или в `data/book-overrides.json`. Вариант B: ввести правило «строка, совпадающая с
названием произведения, — подзаголовок»; цена — лишнее правило и риск ложных срабатываний на
других текстах. Если владелец выберет B, это отдельное изменение после S1.

## Ревью (обязательно)

Шаг закрывает не исполнитель. После кода и зелёных гейтов работа уходит на независимое
ревью роли `reviewer` (скилл `pipeline-reviewer`): он читает план §S1 и код, а не отчёт
исполнителя — отчёт источником фактов не считается.

- Вердикт: **APPROVE** или **REQUEST_CHANGES**, третьего нет.
- При REQUEST_CHANGES шаг остаётся открытым: находки правятся в тех же четырёх файлах,
  гейты G0-G6 прогоняются заново, ревью повторяется.
- Строка «ЗАКРЫТ» в журнале плана и коммит закрытия — только после APPROVE, и их делает
  страж конвейера, не исполнитель.
- Ревьюер обязан проверить отдельно: (1) текст 17 произведений не потерял ни знака —
  пересчитать сверку своим скриптом; (2) 388 стихов и 8 коротких текстов не изменились —
  `git diff` по `scripts/build.mjs` и выборочный `diff` двух dist-страниц; (3) правила БП1-БП7
  не подогнаны под числа из таблицы ожиданий; (4) в `verify` не ослаблено ни одной прежней
  проверки.
