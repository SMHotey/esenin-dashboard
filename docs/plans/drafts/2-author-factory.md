## Цель

Одна команда с именем автора — `wr new --author "Борис Пастернак"` — доводит дело до
живого проекта, а не до каркаса: отдельный репозиторий и домен, конфиг и данные из пакета
автора, `npm run verify` с нулём ошибок, партнёрский каталог с корректными ссылками и
маркировкой, очередь публикаций на 14 будних дней, собственный конвейер `.pipeline`
(профиль `writer`), деплой на GitHub Pages, подтверждённые поисковики, метрика и запись
в реестр сети. Правила серии при этом не переписываются в каждом проекте: они живут в
реестре правил фабрики, проверяются гейтами и переносятся в новый сайт установкой, а не
памятью агента. Любая правка, сделанная позже в любом сайте сети, попадает в шаблон,
в реестр правил и в очередь дополнений этого плана — поэтому план остаётся живым
документом, а не снимком на дату.

## Принципы фабрики

1. **Один код — разные сайты.** Различия живут в данных (`data/*.json`, `content/`), конфиге
   и скине, а не в ветке шаблона. Скопированный `scripts/*.mjs` без версии — дефект.
2. **Шаблон — артефакт с версией.** Каждый сайт знает свою `templateVersion`; `verify`
   предупреждает об устаревшей, но не блокирует деплой. Обновление — по списку из реестра.
3. **Сайт не должен выглядеть клоном.** Свои тексты-каркасы, свой набор и порядок разделов,
   свои аннотации книг, разные расписания, запуск по одному, `/friends/` с переписанными
   описаниями и без ссылочной простыни в подвале.
4. **Права первичны.** Статус автора (`pd` / `protected_until`) — поле реестра; от него
   зависит, что вообще попадает в библиотеку.
5. **Факт без источника не публикуется.** Каждая дата и цитата — со ссылкой; цитата
   сверяется с корпусом, а не с памятью.
6. **Ценность, а не пересказ.** Не меньше 60% описательных страниц — T1–T4 (документ,
   расчёт, синтез, разбор); тексты произведений в эту долю не входят.
7. **Партнёр — данные, а не код.** `data/partners.json` + адаптер; выключение партнёра
   убирает его кнопки без правки шаблона.
8. **Один сайт в 3–4 недели**, следующий — после индексации предыдущего; расширение сети
   по правилу трафика (`NETWORK-PLAN`, п. 9.5).
9. **Правка = правило = шаблон = все сайты.** Новая находка без записи в реестр правил и
   без гейта считается незакрытой.
10. **Конвейер у каждого сайта свой**: своя борда, свой порт UI, своё состояние; общий —
    только профиль `writer` и код фабрики.

   проверка «не клон»; полная система скинов — отдельный план после третьего сайта.

   `check_task_prompt.py` не считается выполненным.
9. Всё, что нельзя проверить командой, файлом или живым адресом, в план не входит.

## Правила, которые фабрика обязана переносить в каждый проект

Эти правила уже оплачены ошибками в Есенине и Бунине; в новом сайте они должны быть
гейтами, а не советами.

1. «Сегодня» — по Москве (`scripts/today.mjs`), иначе UTC-runner отдаёт дату из будущего.
2. `dateModified` меняется только при содержательной правке; массовая «годовщина» без диффа запрещена.
3. Цитату сверять с корпусом (`works.json`), а не с памятью; `\b` для кириллицы не работает.
4. Год написания и год первой публикации — два разных факта.
5. Метр, возраст, «первый/единственный» — считать, а не слышать.
6. У каждой карточки есть изображение; фото — только свободная лицензия с автором, лицензией и ссылкой.
7. Пул публикаций пишется заново, а не find/replace: темы прежнего автора в новый календарь не переезжают.
8. Служебные поля данных (например `source`) — такая же витрина; вики-разметка и `&nbsp;` чистятся скриптом и гейтом.
9. Сырой HTML и dev-пути (`scripts/…`, `npm run …`, `reports/…`) в текстах для читателя — ошибка сборки.
10. Правка одного сайта проверяется и переносится во все остальные; гейт переносится вместе с правкой.
11. Партнёрская ссылка без `erid`/раскрытия, мёртвая ссылка и публикация цены — красный `verify`.
12. `dist` — артефакт; инвентаризация и расчёты пишут в `reports/`, а не в репозиторий.

## Как обновляется этот план

- Источник правил — `factory/rules.json` (машинный) и `docs/FACTORY-RULES.md` (для чтения).
  Каждое правило: `id`, формулировка, источник (скилл/инцидент/Конституция), гейт, где
  внедрено (`esenin`, `bunin`, `template`), статус. Правило без гейта — не правило, а
  очередь: оно обязано получить проверку или быть снято.
- Еженедельный `factory-drift` (cron профиля `writer`) сравнивает сайты по гейтам, скриптам,
  ключам конфига и обязательным файлам данных, пишет `docs/FACTORY-DRIFT.md` и дописывает
  раздел «Очередь дополнений» ниже. Отчёт не меняет сайты и не заводит шагов.
- Очередь дополнений — единственный законный вход для новых работ: владелец (или агент по
  его слову) превращает пункт в шаг `S14+` с «Файл», «Гейты» и «Готово =», после чего
  конвейер исполняет его на общих основаниях. Пункт без шага остаётся видимым долгом.
- Правка, сделанная в любом сайте (включая будущие), в той же сессии: (1) чинится и
  проверяется `verify` там, где найдена; (2) переносится в `factory/template/`;
  (3) получает правило или обновляет существующее; (4) прогоняется по остальным сайтам;
  (5) фиксируется в журнале плана. Пропущенный пункт ловит `drift`, а не память.
- Раз в квартал: ревизия `templateVersion`, обновление старых сайтов по реестру, пересмотр
  правил, потерявших смысл (правило со статусом «устарело» удаляется вместе с гейтом).
