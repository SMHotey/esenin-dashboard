# Следующий шаг плана без ручного контекста

Одна команда в новой сессии — и агент сам собирает контекст и продолжает план.
Шаг определяется по журналу, а не по памяти: сессии не делят контекст.

## Команды

```
python .pipeline/next_step.py                # полный пакет контекста шага
python .pipeline/next_step.py --brief        # короткая версия
python .pipeline/next_step.py --json         # машинный формат (его читает страж)
python .pipeline/next_step.py --list         # все шаги плана и статус
python .pipeline/next_step.py --list-plans   # все планы: следующий шаг, закрыто
python .pipeline/next_step.py --plan 3 --step S2   # принудительно конкретный шаг
```

## Процедура (порядок обязателен)

0. **Прочитать постановку шага** — в карточке строка «ПОСТАНОВКА (прочитать ПЕРВОЙ, до
   кода): `<prompts_dir>/<дата>_<план>-<шаг>_prompt.md`». В ней границы, стоп-сигналы и
   формат отчёта, которых нет в сжатом контракте карточки. Расхождение постановки с
   планом/кодом — зафиксировать в отчёте и не расширять объём. Шага без постановки не
   начинать: страж в этом случае стоит в инциденте, код не писать.
1. **Собрать контекст**: `python .pipeline/next_step.py`. Не угадывать шаг по памяти.
2. **Прочитать**: файлы из блока «Что прочитать», раздел шага в файле плана.
3. **Загрузить рабочие скиллы** по теме шага (стек, тесты, миграции проекта).
4. **Выполнить шаг** минимальными правками. Тесты — контракт: существующие не менять
   и не удалять, новые добавлять (happy path + границы + минимум один интеграционный).
5. **Прогнать гейты шага** ровно как в контракте и показать фактические результаты
   (не пересказ).
6. **Закрыть карточку** через `kanban_complete`: что сделано, прогоны с цифрами, sha.
   Строку журнала НЕ добавлять — её пишет страж после APPROVE ревьюера.
7. **Коммит и пуш — часть шага.** Коммитить ТОЛЬКО файлы шага (`git add <файлы>`,
   НЕ `git add -A`: в дереве бывают правки параллельной сессии), сообщение на языке
   проекта по существу шага.

## Автономный конвейер: шаг → ревью → следующий шаг

`python .pipeline/gate.py` крутится cron-джобой (`--no-agent`, каждые 10 минут).
Ревьюер — сотрудник, страж — детерминированный скрипт: суждение выносит `reviewer`,
решение «ехать дальше» принимает код по машиночитаемому вердикту.

Один тик = одно действие:

| Состояние | Действие стража |
|---|---|
| карточки шага нет | карточка шага (профиль исполнителя), `--max-runtime` из конфига |
| нет постановки шага | карточка промптеру + инцидентный стоп |
| шаг `done` | карточка ревью (профиль ревьюера) |
| вердикт APPROVE | строка журнала + коммит/пуш; следующий шаг — на следующем тике |
| REQUEST_CHANGES (1-й) | карточка правок — единственный авто-круг; находки продублированы комментарием в этой карточке |
| REQUEST_CHANGES (2-й) | стоп + уведомление владельцу |
| шаг/ревью упало, вердикт не распознан | стоп + уведомление |

```
python .pipeline/gate.py --status          # состояние и решение (ничего не меняет)
python .pipeline/gate.py --plans           # таблица планов
python .pipeline/gate.py --run             # один тик вручную
python .pipeline/gate.py --stop "причина"  # остановка после текущего шага
python .pipeline/gate.py --resume          # снять остановку
python .pipeline/gate.py --hold S3         # шаг требует ручного допуска владельца
```

Правила конвейера:

- **Вердикт — единственный машиночитаемый источник**: `<reviews_dir>/<план>-<шаг>.md`,
  ровно одна строка `## ВЕРДИКТ: APPROVE` / `## ВЕРДИКТ: REQUEST_CHANGES`.
  Две строки или цитата чужого вердикта = `AMBIGUOUS` → стоп (конвейер не угадывает).
- **Исполнитель коммитит до закрытия карточки** — ревьюер проверяет коммит, а не
  рабочее дерево.
- **Страж коммитит только** файл плана и файл ревью. Посторонние правки в дереве
  перечисляются и остаются нетронутыми.
- **Цепочка строится лениво**: следующий шаг создаётся только после APPROVE.

## Переписка в карточках

Находки ревьюера читаются в комментарии карточки правок:
`hermes kanban --board <слаг борды> show <id карточки>`. Отчёт
`docs/reviews/<план>-<шаг>.md` остаётся формальным артефактом и единственным источником
находок — его не переписывать.

Ответ на каждую находку — комментарий в ту же карточку по её номеру:
`hermes kanban --board <слаг борды> comment <id карточки> "<номер>: что сделано, файл:строка"`.
Карточку закрывать `kanban_complete` с перечнем закрытых находок. Если комментарий не
отправился (предупреждение `[comment]`), итог всё равно закрывается: это предупреждение,
а не остановка конвейера.

## Стоп-фраза владельца

Фраза «остановка после выполнения шага» в ЛЮБОЙ сессии = `python .pipeline/gate.py --stop
"<фраза>"`. Сессии не делят контекст, поэтому фраза обязана материализоваться в файл
состояния (`<state>/plan_<N>_stop.json`) — иначе следующая сессия её не увидит.
Стоп НЕ рвёт текущий шаг: он доводится до ревью и строки журнала, а следующий не
начинается. «Продолжай» / «снимаю остановку» = `--resume`.

**Ручной допуск шага ≠ стоп-флаг.** Шаг из `--hold` держит конвейер в `idle` с причиной
«в списке ручного допуска владельца»: слова владельца «продолжи выполнение плана» и есть
допуск — снять `--unhold <ШАГ>` и работать шаг.

## Мультиплан

Конвейер ведёт любой план из `<plans_dir>/` с распознанным журналом. Ведомые планы
задаются `driven_plans` в `pipeline.json` (или `PIPELINE_PLANS`): новый файл плана сам
не стартует — иначе черновик начал бы исполняться на следующем тике cron.

```
python .pipeline/gate.py --plans             # все планы: шаг, закрыто, стоп-флаг
python .pipeline/gate.py --plan 3 --status   # состояние конкретного плана
python .pipeline/next_step.py --list-plans   # планы + следующий открытый шаг
```

Стоп-флаг одного плана не блокирует другие. Планы исполняются параллельно, но
совместимость двух шагов проверяет агент, а не страж: (1) файлы шагов не пересекаются;
(2) ресурсы БД не конфликтуют; (3) тяжёлые прогоны тестов — по одному за раз.

## Грабли

- **Дочерний агент делит terminal-сессию с родителем.** Proof-скрипт, сделавший
  `export PIPELINE_STATE_DIR=...` или `PIPELINE_KANBAN_DB=...`, оставляет переменные
  в родительской сессии: страж начнёт читать чужое состояние. После делегирования —
  `env | grep PIPELINE` и `unset` лишнего.
- **Снятый стоп упирается в старую карточку шага.** Если карточка осталась в `blocked`,
  после `--resume` страж не создаст новую, а уйдёт в стоп «карточка шага … в статусе
  blocked». Порядок: `--hold <ШАГ>` (иначе тик поднимет второго исполнителя) →
  `--resume` → работа в сессии → закрыть старую карточку
  `hermes kanban --board <борда> complete <id> --result "…"` → `--unhold <ШАГ>` → `--run`.
- **Инцидентный стоп снимается сам, владельческий — нет.** В стоп-файле есть `kind`:
  `owner` (только `--resume`) и `incident` (страж снимает, как только причина ушла;
  повторно не уведомляет).
- **Тесты стража не должны трогать боевые пути.** `Paths` собирается из конфигурации
  в момент вызова; иначе `monkeypatch` не действует и тест ставит НАСТОЯЩИЙ стоп-флаг.
- **`--hold/--unhold/--stop/--resume` без `--plan`** пишут в состояние ПЛАНА ПО
  УМОЛЧАНИЮ. Для соседнего плана обязателен `--plan <N>`: иначе ручной допуск окажется
  у чужого плана, а нужный шаг пойдёт в работу молча.
- **Экономия контекста (каждая карточка — новая сессия, платим за токены вывода).**
  Вывод команд ≤ 200 строк: `pytest -q --tb=line`, `git status --porcelain | head -30`,
  большой вывод — в файл и `grep` по нему. Уже прочитанный файл не перечитывать целиком.

## Если шаг оказался больше оценки

Остановиться, записать в отчёт фактическое состояние («выполнено частично: …»), не
закрывать карточку как `done`, и предложить владельцу разбиение на подшаги.
Растягивать «почти готово» запрещено.
