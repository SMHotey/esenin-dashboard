# План, который конвейер сможет вести

Конвейер читает план как данные. Если файл написан «прозой», страж его не увидит:
план не появится в `--plans`, шаги не соберутся, карточки не создадутся. Ниже —
жёсткий формат и минимум, без которого шаг не стартует.

## Файл и имя

`<plans_dir>/<НОМЕР>-<слаг>.md`, например `docs/plans/3-billing.md`. Номер — 1–2 цифры,
дальше дефис. По номеру строятся файлы состояния (`plan_3_state.json`) и имена отчётов
ревью (`docs/reviews/3-S1.md`).

## Обязательные два раздела

### 1. Раздел шагов

Заголовок уровня 2 со словом-маркером («Шаги», «Шаги плана»). Внутри — по заголовку
на шаг:

```
## Шаги

### S1. Схема счёта и миграция (1 дн) `executor`

- Файл: `app/models/invoice.py`, `migrations/0007_invoice.py`
- Тесты/гейты: `python -m pytest tests/test_invoice.py -q` → 8 passed
- Готово = таблица `invoice` создана миграцией, 8 тестов зелёные, downgrade -1 проходит
- Важно: существующие счета не пересчитывать
```

Правила разбора (по ним работает `next_step.py`):

- идентификатор шага — `S1`, `T10`, `E15a`, `S25-8` (буквы + номер + необязательная буква);
- `(2 дн)` в заголовке — оценка; `` `executor` `` в заголовке — профиль-исполнитель
  (по умолчанию берётся `profiles.driver` из `pipeline.json`);
- пункт с меткой «Файл» даёт список файлов шага (пути в обратных кавычках);
- пункты «Тесты», «Гейты», «Проверка» дают блок гейтов — дословно в карточку и в ревью;
- строка «Готово = …» задаёт критерий приёмки; без неё ревьюер не сможет вынести
  вердикт по контракту;
- первый содержательный пункт становится «целью» шага — пиши его как результат,
  а не как процесс.

Шаг = один проверяемый результат. Если «Готово =» нельзя проверить командой, файлом
или значением — это не шаг, а пожелание.

### 2. Раздел журнала

Заголовок уровня 2 со словом «Журнал». Таблица ровно с пятью колонками и
идентификатором шага ВО ВТОРОЙ:

```
## Журнал выполнения

| Дата | Шаг | Коммиты | Прогоны и доказательства | Статус |
|---|---|---|---|---|
| — | S1 | — | — | открыт |
```

Страж дописывает строку сам после APPROVE: `| 01.11.2026 | S1 (Схема счёта) | abc1234 | ревью ... | ЗАКРЫТ |`.
Статус, начинающийся с «ЗАКРЫТ», — единственный признак закрытого шага. Руками строки
не добавлять: это работа стража, иначе ревью обходится.

## Чего в плане быть не должно

- Шагов без «Готово =» — их нельзя принять.
- Двух шагов с одинаковым идентификатором — карточки получат одинаковые ключи.
- Шага, который правит чужую область без пометки: параллельные шаги проверяет человек
  (`--hold`), страж совместимость не считает.
- Задач «исследовать и решить» — исследование делает промптер на этапе постановки.

## Режим планирования

Прежде чем писать план, проверь режим: `hermes pipeline plan-mode status`.

- «Режим планировщика: on» — планировать можно.
- «off» — план не писать: скажи владельцу, что включение это
  `hermes pipeline plan-mode on` (действует со следующей сессии).

Порядок работы:

1. **Уточнения.** Спрашивать только то, что меняет состав шагов или критерий приёмки.
   Не больше пяти вопросов за раз, у каждого варианта — метка `(рекомендуется)`.
2. **Допущения.** Неясность не додумывать молча: выписать её в блок «Допущения» и
   показать владельцу вместе с планом.
3. **Черновик.** Писать в подкаталог `drafts/` каталога планов (для этого проекта —
   `docs/plans/drafts/`), имя — по правилу раздела «Файл и имя». Страж подкаталог не
   читает (`plans_dir.glob` без рекурсии), поэтому черновик сам не начнёт исполняться.
4. **Линтер.** `hermes pipeline doctor --plan <путь к черновику>` → «ИТОГ: OK». После
   шага S6 то же делает `hermes pipeline plan --check`.
5. **Предъявление.** Владельцу показываются список шагов, допущения и то, что не
   проверено. Дальше — ждать подтверждения, а не начинать исполнение.

**Агент не утверждает план сам.** Он не переносит файл из `drafts/`, не пишет строку в
журнал и не коммитит план. Перенос делает владелец командой
`hermes pipeline plan --accept <номер плана>`.

## Планирование = ещё не исполнение

Пишешь план — не правь код. Каждый шаг исполняется отдельной сессией по постановке
роли `prompter` (скилл `pipeline-prompter`), затем ревью роли `reviewer`. Это
записывается в «Готово =» шага строкой: «постановка в `<prompts_dir>/` прошла
`check_task_prompt.py`».

Проверка после написания:

```
python .pipeline/next_step.py --list-plans     # план виден, следующий шаг назван
python .pipeline/next_step.py --plan <N> --list
```
