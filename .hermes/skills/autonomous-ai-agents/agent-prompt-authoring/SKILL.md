# Идеальный промт для агента-программиста

Промт — это не пересказ плана и не «постановка своими словами». Это передача
контекста: агент-исполнитель не видел твоей сессии, не знает, что ты уже проверил,
и не имеет права догадываться. Промт хорош ровно настолько, насколько исполнитель
после него делает правильную работу с первого раза и не изобретает лишнего.

Скилл отвечает за **как писать**; что именно требует шаг — берётся из плана.
Обратная сторона (как исполняют присланный промт) — `pipeline-next-step`.

## Когда применять

- Шаг плана передаётся другому агенту (программист, воркер канбана, `delegate_task`,
  Codex/Claude Code/OpenCode).
- Задача формулируется в чат «на словах» и должна стать исполнимой постановкой.
- Нужно восстановить постановку после разрыва сессии.

Не для: диалога в одном контексте, код-ревью (`pipeline-reviewer`), плана на несколько
шагов (`pipeline-plan-authoring`).

## Принципы

1. **Контекст вместо инструкций.** Главный дефицит агента — не интеллект, а контекст.
   Разделяй фазы: исследование → постановка → исполнение. Промт несёт результат
   исследования, а не приглашение его повторить.
2. **Один промт = один срез.** Объём — одна сессия исполнителя и один проверяемый
   результат. Пять несвязанных правок в одном промте дают половину сделанного и отчёт
   «остальное потом».
3. **Факт отдельно от гипотезы.** Проверенное помечается как факт с командой и выводом.
   Остальное — «предположение, проверить». Исполнитель обязан знать, что можно
   принимать на веру, а что обязан перепроверить.
4. **Указатели, а не дампы.** Вместо пересказа кода — `path:line`, имя символа, точная
   команда. Вместо «рядом есть похожий сервис» — `services/foo.py::bar`.
5. **Контракт «Готово =» проверяемый.** Пункт, который нельзя проверить командой,
   файлом или значением, — не критерий, а пожелание. Тесты утверждают значения, а не
   присутствие ключей.
6. **Гейты — точной командой и ожидаемым числом.** «Прогнать тесты» не гейт.
   `python -m pytest tests/test_x.py -q` → ожидаемо `12 passed`, вывод в файл, `EXIT`
   смотреть по pytest, а не по хвосту пайпа.
7. **Стоп-сигналы обязательны.** Промт заранее говорит, при каком расхождении
   исполнитель останавливается и докладывает, а не «адаптирует по смыслу».
8. **Эталон вместо прилагательных.** «Пиши чисто» не работает. Работает ссылка на
   существующий образец: `tests/test_offers.py::TestX` как эталон стиля, конкретный
   DTO как эталон формы.
9. **Никакой воды.** Каждая строка должна менять поведение исполнителя. «Будь
   внимателен», «следуй лучшим практикам» — удалить и заменить проверяемым критерием.
10. **Формат отчёта и язык заданы заранее.** Отчёт до коммита, по пунктам, с цифрами
    прогонов; язык — язык проекта.
11. **Вопросов не больше трёх и каждый — с ценой.** Открытый вопрос без вариантов и
    оценки останавливает работу.
12. **Окружение — часть промта.** Оболочка, интерпретатор (`/path/to/venv/bin/python`),
    рабочая директория, запрет на сборки и прод-операции, бюджет времени.

## Процедура написания (5 фаз, у каждой критерий завершения)

1. **Контракт.** Выписать из раздела плана: цель, «Готово =», гейты, файлы, запреты,
   коллизии, журнал выполнения.
   *Готово:* каждый пункт получил id `C1..Cn`, ни один не остался пересказом.
2. **Recon факта.** По каждому `Cn` проверить реальное состояние: существует ли
   файл/символ/таблица, что уже сделано, что противоречит плану. `search_files`,
   `read_file`, `git log/show`.
   *Готово:* у каждого `Cn` есть либо подтверждение фактом, либо пометка «предположение».
3. **Разрывы.** Список того, чего для исполнения не хватает: неясные имена,
   отсутствующие данные, конфликт плана с правилами проекта, неоднозначная трактовка.
   Для каждого — решение по умолчанию или вопрос.
   *Готово:* разрывов без решения и без вопроса ноль.
4. **Черновик** по шаблону `templates/task-prompt.md`, блоки в том же порядке.
   *Готово:* все обязательные блоки на месте, включая «Стоп-сигналы» и «Формат отчёта».
5. **Гейт самопроверки** по чек-листу ниже; машинный гейт —
   `python .pipeline/check_task_prompt.py <файл>`.
   *Готово:* чек-лист пройден целиком, гейт `PASS`.

## Обязательные блоки промта (9; девятый — «Ревью»)

| Блок | Что внутри | Признак плохого блока |
|---|---|---|
| Роль и цель | кто исполнитель, один абзац результата | «сделай красиво/правильно» |
| Контекст-факты | репозиторий, ветка, SHA, окружение, что уже сделано (с командами) | пересказ истории сессии |
| Границы | что можно менять, что запрещено, чего не делать вовсе | «старайся не ломать» |
| Задачи | нумерованные шаги с `path:line` и ожидаемым результатом | список тем без адресов |
| Гейты | точные команды + ожидаемые числа + как читать код возврата | «прогнать тесты» |
| Стоп-сигналы | условия остановки и что доложить | отсутствует |
| Формат отчёта | порядок разделов, обязательные цифры | «расскажи, что сделал» |
| Вопросы | ≤3, с ценой вариантов | вопрос без вариантов |
| Ревью | кто ревьюит, вердикт, что при REQUEST_CHANGES | блок отсутствует |

Шаблон: `templates/task-prompt.md`.

## Чек-лист самопроверки (гейт перед выдачей)

1. Исполнитель по промту может начать, не задавая ни одного уточняющего вопроса?
2. Каждый пункт «Готово =» имеет проверку (команда / файл / значение)?
3. Все адреса (`path:line`, символы, таблицы) проверены в текущем дереве?
4. Числа в промте — замер или явно помечены как ожидание?
5. Запреты перечислены явно (миграции, данные, тесты, сборки, коммит)?
6. Стоп-сигналы сформулированы так, что их нельзя обойти «по смыслу»?
7. Формат отчёта задан, включая отчёт до коммита и строки прогонов?
8. Нет ни одной строки-лозунга, которая не меняет поведение?
9. Объём = один срез; несвязанное вынесено в «не входит в эту задачу»?
10. Язык, окружение и интерпретатор названы?
11. Вопросы ≤3 и каждый с ценой вариантов?
12. Промт не противоречит плану и правилам проекта? Противоречие названо, а не сглажено?

## Ревью в постановке (обязательный девятый блок)

Последний блок промта — «Ревью (обязательно)»: шаг закрывает не исполнитель, а роль
`reviewer` (`pipeline-reviewer`) по плану и коду. В блоке указать: кто ревьюит, что
ревьюеру доступно (план + код; отчёт исполнителя — не источник фактов), формат
вердикта (APPROVE / REQUEST_CHANGES) и что при REQUEST_CHANGES шаг остаётся открытым.
Постановка — единственный вход исполнителя; если ревью в ней не названо, шаг
закрывается «на словах».

## Антипаттерны

| Антипаттерн | Почему плохо | Как правильно |
|---|---|---|
| Дамп файлов «чтобы агент увидел всё» | шум вытесняет контракт | адреса + 5–10 строк сути |
| Рецепт вместо результата («создай класс X с полем Y») | ломается о фактический код | результат + критерий + образец |
| «Сделай по аналогии, разберёшься» | агент выберет другой аналог | назвать образец и что копировать |
| Критерий «тесты зелёные» | зелёный можно получить ослаблением | какие тесты, сколько, какие значения |
| Противоречия внутри промта | исполнитель выберет удобное | противоречие назвать и отдать решение |
| Промт-дубль плана | два источника истины расходятся | план = требования, промт = исполнение |
| Скрытые решения («очевидно же») | исполнитель догадается иначе | решение записать строкой «решение» |
| Промт без границ | агент залезет в соседнюю подсистему | блок «Запреты» + «не входит в задачу» |

## Специфика проекта

Правила конкретного проекта (что нельзя менять, какие миграции разрешены, какие
данные священны) берутся из `AGENTS.md` и доков архитектуры и идут в блок «Границы»
дословно по смыслу. Шаблон фрагмента для `AGENTS.md` нового проекта —
`templates/AGENTS-pipeline-fragment.md`.

## Проверка (что промт годен)

- `python .pipeline/check_task_prompt.py <файл>` → `ИТОГ: PASS`.
- Прогон чек-листа выше — 12/12.
- Пробное чтение «глазами исполнителя»: пройти промт сверху вниз и на каждом шаге
  ответить, что именно делать и чем проверить. Где ответа нет — там дыра промта.
